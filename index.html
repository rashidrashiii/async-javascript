1Why async?

Many things a program does take time: loading data from a server, reading a file, waiting for a user to click, or waiting for a timer. JavaScript runs one line at a time. If it stopped and waited for a slow server, the whole page would freeze, and buttons, scrolling and typing would all stop working.

So JavaScript does something smarter. It starts the slow task, carries on with the rest of the code, and comes back when the task is finished. Code that works this way is called asynchronous, or async.

Analogy: the washing machine

You don't stand in front of the washing machine for 45 minutes. You start it, go and do other things, and come back when it beeps. JavaScript treats slow tasks the same way.

Key idea

Async code runs later, only after the code that is currently running has finished. setTimeout hands the function to the browser, and when the time is up the function waits in a queue until JavaScript is free. This queue-and-wait system is called the event loop.

2Callbacks

A callback is a function you pass to another function, so that it can be called later. It was the first way JavaScript handled async work, and you already used one above: the arrow function given to setTimeout.

Analogy: "call me back"

You order a cake and give the shop your phone number. You don't wait at the counter; they call you back when it's ready. The callback is your phone number.

Why undefined? The return happens straight away. The book only arrives one second later, when nobody is waiting for it any more.

Error-first callbacks

Things can go wrong: the server is down, or the ID doesn't exist. The common convention (from Node.js) is that the callback's first argument is the error. If everything went fine, the error is null and the data comes second.

3Callback hell

Callbacks work well for a single task. Real apps often need several steps in order, where each step needs the result of the previous one: get the book, then its author, then the author's other books. With callbacks, each step goes inside the previous one.

Look at the shape of the code: it keeps drifting to the right. This is called callback hell or the pyramid of doom. Its problems are:

  • It's hard to read, and gets worse with every extra step.
  • The same error handling is repeated at every level.
  • Running tasks at the same time (in parallel) is awkward.
  • Pieces are hard to reuse or rearrange.

JavaScript gave us a better tool to fix this: Promises.

4Promises

A Promise is an object that represents a value that will arrive in the future. Instead of passing a callback in, the function hands a Promise back straight away, and you decide what to do when it settles.

Analogy: the food court token

You order at a food court and get a token. The token isn't food, but it's a promise of food. While the food is cooking the token is pending. Then either your food arrives (fulfilled) or they tell you it's out of stock (rejected).

StateMeaningFood court
PendingStill workingFood is being cooked
FulfilledSucceeded, has a valueFood is ready
RejectedFailed, has a reason (an error)"Sorry, out of stock"

A Promise settles only once: after it is fulfilled or rejected, it never changes again. The dot on each output panel on this page uses these same colours.

Creating and using a Promise

You create a Promise with new Promise(...). Inside, you get two functions: call resolve(value) for success, or reject(error) for failure. To use the result, chain these methods:

  • .then() runs when the Promise is fulfilled.
  • .catch() runs when it is rejected.
  • .finally() runs either way, which is handy for clean-up like hiding a loading spinner.

Chaining: the cure for callback hell

.then() always returns a new Promise, so you can chain another .then() after it. If you return a Promise from inside .then(), the next step waits for it. The result is flat code that reads top to bottom, with a single .catch() for every step.

Try this: change getBook(1) to getBook(-1). One .catch() handles the error, and the later steps are skipped. Compare this with the callback pyramid in chapter 3.

Ready-made Promises

Promise.resolve(value) and Promise.reject(error) create a Promise that is already settled. Notice that even then, .then() and .catch() still run after the current code finishes.

What you return is what the next step gets

Return a plain value and the next .then() receives it immediately. Return a Promise and the next .then() waits for it to settle, then receives its value.

Throwing errors in a chain

If you throw inside a .then(), the Promise becomes rejected. The chain skips the remaining .then() steps and jumps to the nearest .catch(). After the .catch(), the chain carries on normally.

Turning a callback function into a Promise

Old code and libraries often use callbacks. You can wrap them in a Promise: call resolve where the callback gives data and reject where it gives an error.

5Async/await

async/await is a nicer way to write Promise code. Underneath it is still Promises, but the code reads top to bottom like normal, synchronous code. Four rules to remember:

  1. Putting async in front of a function makes it asynchronous.
  2. await means "pause this function here until the Promise settles, then give me its value".
  3. await only works inside an async function (or at the top level of an ES module).
  4. An async function always returns a Promise.

Error handling with try/catch

With await, a rejected Promise behaves like a thrown error, so you handle it with the familiar try/catch/finally. They line up with the Promise methods you already know: try is the success path like .then(), catch is .catch(), and finally is .finally().

Handling different kinds of errors

Errors have types. instanceof lets you react differently to each one, for example invalid JSON (SyntaxError) versus a problem you detected yourself (Error).

A real request with fetch

Watch out: fetch only rejects when the network itself fails. A 404 or 500 response still counts as "success", so always check response.ok yourself.

Top-level await

Inside ES modules (<script type="module"> or files that use import/export), you can use await outside a function. In a normal script, await must be inside an async function.

6Sequential vs parallel

Each await pauses until its Promise is done. If you await three independent requests one after another, you wait for all three in a row. Promise.all starts them together and waits until they have all finished.

Analogy: making breakfast

You could boil the eggs, then make the toast, then make the tea. Or you could start all three at once and finish much sooner. But you can't butter the toast before it's toasted, because some steps depend on others.

Notice: the total time of a parallel load is roughly the time of the slowest request, not the sum of all of them.

When to use which: go sequential when a step needs the previous result (you need the book before you know its authorId). Go parallel when the tasks don't depend on each other. Real pages usually mix both.

8Error handling patterns

A few patterns come up again and again in real apps.

A wrapper that returns [data, error]

Instead of writing try/catch everywhere, wrap the Promise once and get back a pair.

Falling back to a default value

Why return await? Remove the await and run it again. Without it, the function returns the Promise before it fails, so the catch never sees the error.

Retrying a failed request

Some failures are temporary, like a busy server. Retry a few times, waiting a little longer each time. Doubling the wait (500 ms, 1 s, 2 s…) is called exponential backoff.

10Recap and practice

Callbacks came first. Promises made them flat and gave us one place to handle errors. Async/await made Promises read like normal code. Underneath, it's all Promises. Here is the same task written all three ways.
